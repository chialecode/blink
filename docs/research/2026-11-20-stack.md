## 1. 总体技术路线对比

### 1.1 系统运行拓扑对比

BLINK 需要同时满足“手机与桌面打开 0ms 无感记录、离线流畅伴读”与“多模态重型解析（网页清洗、EPUB/PDF 解析、语音转写、OCR、夜间睡眠期 Agent 演化）长期稳定运行”。

| 方案 | 优点 | 缺点 / 取舍 |
| --- | --- | --- |
| **五端离线薄客户端 + 自托管家庭常驻大脑 `blink-hub` + Tailscale 虚拟局域网（选定，DEC-013、DEC-014）** | 端侧 SQLite（`drift`）保障断网 0ms 读写与全文检索；Whisper 语音转写、OCR、正文抓取、向量嵌入与夜间定时合成全部在常驻家庭主机执行，不耗手机电量、不受 iOS/Android 后台杀进程限制；服务端 Agent 提示词与工作流演进无需重编重签五端客户端；Tailscale（WireGuard）免公网端口暴露即可跨外网安全同步 | 需要一台常驻家庭主机（NAS、Mini-PC 或自管 Linux 主机，Docker Compose 一键拉起，见 [USER-ACTIONS.md](https://github.com/chialecode/blink/issues?q=is%3Aissue+label%3Aneeds-user) `Q-002`）；端侧需实现可靠的离线 Outbox 同步队列 |
| 纯端侧重客户端（手机与桌面各自跑本地模型、爬虫与点对点同步） | 无需家庭常驻节点 | iOS/Android 严格限制后台常驻与大内存占用，无法执行夜间睡眠合成与大模型推理；手机跑语音转写与全文向量化发热耗电严重；五端各自抓取网页易因移动端网络切换中断 |
| 传统公网 SaaS 云端集中式架构 | 客户端最薄 | 需暴露公网服务并承担攻击面；个人日记与私密思考离开自有硬件，违背本地优先与 `#private` 物理主权原则（[需求规格](../requirements.md#product)） |

### 1.2 五端客户端框架对比（`Windows + Android + Linux + macOS + iOS`）

| 方案 | 优点 | 缺点 / 取舍 |
| --- | --- | --- |
| **Flutter 3.x / Dart 3.x（选定，DEC-015、DEC-021）** | 官方一等公民覆盖全部五个目标平台；Skia / Impeller 自绘渲染保证中文字体排版、双栏伴读分屏与移动端半屏抽屉像素级一致；`dart:ffi` 直接零开销绑定原生 SQLite3（FTS5）与 PDFium（`pdfrx`）；单套状态树（`flutter_riverpod`）与测试工具链成熟 | 存在两个已知行业陷阱：① 重型富文本编辑器在移动端中文输入法组合态（CJK IME）下易吞字跳光标；② Linux GTK 桌面端 WebView 插件生态薄弱。BLINK 在架构层采用双层内容格式显式拆解：手写采集层坚持纯文本/轻量 Markdown 原生流输入，外部阅读块与 AI 综述视图采用服务端 `nh3` 白名单受控语义 HTML + 客户端 `super_sliver_list` 与 `flutter_widget_from_html` 纯原生组件树渲染，既保留跨行列合并表格、内联 SVG 与折叠抽屉排版，又彻底绕开两处短板 |
| Tauri 2.0（Rust + 系统 WebView + Web 前端） | 桌面安装包体积小；浏览器 DOM/CSS 对复杂网页兼容性好 | 强依赖五端各自的系统 WebView（WebView2、WKWebView、WebKitGTK、Android WebView），Linux 渲染差异、移动端软键盘顶起延迟及跨段落长文选区锚点在不同内核间行为碎片化；同时维护 Rust 与 TypeScript 双端侧栈 |
| Kotlin Multiplatform + Compose Multiplatform | Android 原生集成最好，Kotlin 共享业务层稳健 | Linux 桌面端与 iOS 端在高性能 PDFium 选区渲染、桌面托盘窗口管理及统一录音插件上的生态成熟度明显弱于 Flutter |
| Electron（Chromium + Node.js） | 桌面端 Web 生态最丰富 | 完全不支持 Android 与 iOS，无法满足五端同构刚需，直接排除 |
| React Native | 移动端生态庞大 | 官方核心不维护 Linux 桌面端，Windows/macOS 依赖独立分支，五端维护与原生 C++ PDF 渲染桥接成本高 |

### 1.3 家庭中枢（`blink-hub`）服务端语言对比

| 方案 | 优点 | 缺点 / 取舍 |
| --- | --- | --- |
| **Python 3.12+（`FastAPI` + `Pydantic v2` + `SQLAlchemy 2 / asyncpg`）（选定，DEC-018）** | 与 `trafilatura` 正文提取、`lxml` EPUB 清洗、`nh3`（Rust `ammonia`）高速 HTML/SVG 安全净化、`pypdfium2`、`faster-whisper`、`RapidOCR`、`pgvector`、`PydanticAI` 及 `LiteLLM` 同处第一原生生态，零跨语言 IPC 胶水；`FastAPI` 原生导出精确 OpenAPI 3.1 规范供 Dart 客户端自动生成强类型契约包 | CPU 密集解析任务受单进程并发限制，需通过后台独立进程池 / Worker 队列隔离 HTTP 协程循环，避免阻塞同步接口响应 |
| Go / Rust API 服务 + Python AI/解析子服务 | 网关二进制体积小、高并发吞吐强 | 个人/家庭单用户同步并发极低（几台设备），瓶颈完全在文档解析与模型推理；拆成双语言服务增加容器编排、内部协议同步与排障负担 |
| TypeScript（Node.js / Bun）服务端 | 异步 I/O 与前后端 JSON 工具成熟 | 本地 `faster-whisper`（CTranslate2）、离线中英文版面 OCR 与高质量正文抽取库在 Node 生态缺乏同等级原生替代，最终仍需外挂 Python 进程 |
